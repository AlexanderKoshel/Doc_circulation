# РГР2 — этап 1. Аудит исходной модели БД

Статус: **готово для локальной проверки**. На этом этапе не выполняются SQL-команды и не меняется существующая модель.

## Основание

- Индивидуальное задание: создать БД в T-SQL, таблицы в 3НФ с PK/UNIQUE/CHECK/NULL/NOT NULL, именованными CONSTRAINT и FK; наполнить **каждую таблицу минимум 10 записями**; диаграммы SSMS, отчёт, SQL-скрипты с комментариями и резервная копия.
- Источники существующей модели: `# База данных \`Doc_circulation_db\` полное описание с группировкой таблиц.md`, `XML scheme.canvas`, `Progress making DB.canvas` в корне репозитория.

## Результат инвентаризации

- Основной Markdown содержит **96 заголовков таблиц** (заголовки уровня `###`) в 10 предметных группах. Это описание модели, **не** 96 проверенных таблиц работающего SQL Server.
- Основные домены: сотрудники и персонал, роли, подразделения, проекты, задачи и время, отпуска и больничные, навыки, оборудование и ресурсы, справочники, отчётность.
- Есть составные PK в таблицах связей (например `EmployeeRoles(EmployeeID, RoleID)` и `Project_SolutionCategories(ProjectID, SolutionCategoryID)`).
- `.canvas` и Markdown не полностью совпадают; их нельзя механически соединять без выбора канонической схемы.

## Замечания, влияющие на реализацию

1. **Неопределённые цели FK.** В Markdown встречаются обозначения `(внешняя таблица)`, `(справочник функций)`, `(справочник)`, `(справочник команд)`, `(справочник статусов)`, `(справочник оборудования)`, `(справочник валют)`. Для SQL Server каждой связи нужна конкретная существующая таблица и PK/UNIQUE-столбец. Не создавать фиктивные FK.
2. **Разночтения схем.** В Markdown у `Employee.JobPositionID` указана ссылка `JobPosition.ID`, а в `XML scheme.canvas` — `JobPositionJunction.ID`; для `Employee` набор полей тоже отличается. В Markdown `EmployeeSkill` имеет отдельный `ID`, а в Canvas описан составной ключ `EmployeeID, SkillID`.
3. **Некоторые таблицы содержат лишь логическую спецификацию.** Пустые длины у `nvarchar`/`varchar` необходимо разрешить до написания CREATE TABLE. Не использовать `nvarchar` без длины по умолчанию (это неожиданно ограничит колонку).
4. **Требование 3НФ не доказано автоматически.** Например, хранение `Employee.FullName` при наличии имени и фамилии нужно оформить как вычисляемое поле, если оно действительно требуется; проверить дублирующиеся сведения и функциональные зависимости.
5. **Объём.** 96 описанных таблиц означают как минимум 960 INSERT-строк для буквального выполнения требования «10 записей в каждую таблицу». Следует сохранять полноту модели либо явно зафиксировать согласованное сокращение предметной области; этот этап ничего не сокращает.
6. **Нет исполнительных SQL-скриптов в исходном дереве `master`.** Их нужно создать далее; наличие диаграммы `.canvas` не заменяет создание диаграммы в SSMS.

## Предлагаемое правило для этапов 2–5

Пока использовать Markdown как исходную спецификацию для SQL, а Canvas как источник замечаний/расхождений. Все изменения модели описывать отдельно, не исправляя молча первоначальные материалы. Сохранять конвенции именований и зависимости. **Это предложение, а не уже утверждённая окончательная SQL-модель.**

## Проверка на локальном компьютере

В корне локального репозитория (PowerShell):

```powershell
git status --short
git fetch origin
git switch rgr2
git pull --ff-only origin rgr2
Get-Content .\reports\rgr2\01_schema_audit.md -Encoding UTF8
```

Убедиться, что указаны 96 таблиц, несовпадения источников, нерешённые FK и оценка объёма. **На этапе 1 SQL Server не нужен**: все операции только чтение. Если `git switch` предупреждает о несохранённых локальных изменениях, сначала сохраните их; не используйте `git reset --hard`.
